# Delhivery Last-Mile Delay Intelligence Pipeline

## 1. How to Run

Clone the repository and open its root directory in a terminal. Create and activate a virtual environment, then install the pinned dependencies:

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -r requirements.txt
```

Run the scripts from the repository root in this exact order:

```powershell
python generate_data.py
python part_a_clean_eda.py
python part_b_regression.py
python part_c_classification.py
python part_d_segments.py
python package_model.py
python predict_delay.py
```

The scripts generate the modelling table, evaluation outputs, packaged model and new-shipment action list. CSV outputs are stored in `outputs/`, while reusable model files are stored in `models/`.

**Model compatibility:** `models/delay_model.pkl` is regenerated by running `python package_model.py`. A committed pickle can be loaded reliably only with the scikit-learn version pinned in `requirements.txt`. If the installed scikit-learn version differs, rerun `package_model.py` to rebuild the model with the local environment before prediction.

## 2. Data Findings

- Raw shipment records: 1,224.
- Exact duplicate rows removed: 24.
- Cleaned shipment records: 1,200.
- Delayed shipments: 278, giving an overall delay rate of 23.17%.
- Missing parcel weights before imputation: 24.
- Scanner-fault parcel-weight sentinel rows identified: 5.
- Missing values in the final modelling features and target: 0.
- **Service type:** Express had the highest delay rate at 48.97%, compared with 20.56% for Standard and 8.57% for Economy.
- **Hub tier:** The observed delay rate rose from 4.00% for Tier 1 to 21.50% for Tier 2 and 44.00% for Tier 3.
- **Distance:** Delay rates were 2.19% for 0–200 km, 13.68% for 201–400 km, 43.64% for 401–600 km, and 85.23% for distances over 600 km.
- **Correlation:** Promised delivery hours had the strongest reported correlation with delivery hours (0.8372), followed by distance in kilometres (0.4013). The third-strongest column must be confirmed from `outputs/part_a_correlations.csv` before submission.
- **Declared value:** The filled declared-value mean was INR 1,533.05 and its median was INR 1,121.50. Because the mean exceeds the median, the distribution is right-skewed. The natural-log transformation reduces the influence of large values and makes this feature less skewed.

## 3. Model Results (Regression)

The dataset was divided into 840 training, 180 validation, and 180 test records.

The selected final model was Linear Regression. Its held-out test results were:

- MAE: 3.5671 hours.
- MSE: 20.4625 hours squared.
- RMSE: 4.5236 hours.
- R-squared: 0.9493.

The test MAE means that the model's absolute prediction error averaged approximately 3.57 hours on this test set. The R-squared value indicates that the model explained approximately 94.93% of the variation in delivery hours in the held-out test data.

Linear Regression had the best validation RMSE in the recorded model comparison (4.8912), narrowly ahead of Gradient Boosting (4.9165). The final model was selected using validation results rather than the test set.

## 4. Model Results (Classification)

The classification pipeline used seven selected features and a Random Forest classifier. The selected configuration was `default_forest_same_7_features`, and the alert threshold was 0.5.

Held-out test results:

- Accuracy: 86.67%.
- Precision: 68.89%.
- Recall: 75.61%.
- F1-score: 72.09%.
- True negatives: 125.
- False positives: 14.
- False negatives: 10.
- True positives: 31.

Precision of 68.89% means that about 6.9 out of every 10 flagged parcels were actually delayed in the test set. Recall of 75.61% means that the model identified about 7.6 out of every 10 delayed parcels.

The test set contained 41 delayed parcels, so the recall estimate is based on a relatively small number of positive cases. Results may vary on future shipments.

The blind baseline predicts that every parcel will arrive on time. Although this can achieve reasonable accuracy when most parcels are on time, it has zero recall for delayed parcels and therefore does not solve the operational problem.

The five bookkeeping columns (`label_print_batch`, `scanner_build_no`, `tape_roll_no`, `sticker_serial_mod`, and `shelf_slot_no`) are treated as noise features. The feature-score and forest-importance outputs should be used to verify that all five fall outside the top seven F-score features and to report their combined importance share.

The feature-selection comparison evaluates K values of 5, 7, 10, 12, and 17. Seven features were retained for the final classifier. The tuning comparison includes grid search, randomized search, and the untuned forest on the same seven features. The untuned seven-feature forest won the recorded validation-F1 comparison. This is a useful reminder that tuning does not guarantee better results, particularly when selection is based on a validation set of only 180 rows.

The threshold was selected for the operational objective of catching delayed parcels while limiting unnecessary alerts. Its validation precision and recall should be interpreted alongside the threshold table, not inferred from test results. The test set was used for final evaluation, not for choosing the threshold.

## 5. Operations Recommendation

### Hub prioritisation

The hub-level analysis identified three operating segments:

- **Escalate:** 9 hubs, with a mean delay rate of 46.00%, mean delivery time of 64.65 hours, and mean distance of 470.48 km. These hubs should receive priority operational review.
- **Watch:** 8 hubs, with a mean delay rate of 15.50%. Monitor their performance and investigate rising delay rates.
- **Standard:** 7 hubs, with a mean delay rate of 2.57%. Continue routine monitoring.

Four hubs do not match the segment implied by their existing tier labels:

- HUB07, Kolkata: Tier 1 but assigned to Watch.
- HUB13, Nagpur: Tier 2 but assigned to Escalate.
- HUB15, Kochi: Tier 2 but assigned to Escalate.
- HUB22, Dehradun: Tier 3 but assigned to Watch.

These mismatches show why tier labels should not be used as the only basis for operational decisions. Actual observed hub performance and segment assignment should also inform prioritisation.

### Why retain three segments?

The business requires three operating playbooks, so K = 3 was retained. In the separation analysis, the across-to-within distance ratio increased from 2.894 for K = 2 to 5.393 for K = 3, then increased further to 6.305 for K = 4 and 6.887 for K = 5. However, K = 4 and K = 5 produce clusters containing fewer than six hubs. Such small groups may not justify separate operating playbooks, so K = 3 provides a practical balance between separation and operational usefulness.

### New-shipment actions

The pipeline scored 48 new shipments. At the 0.5 threshold:

- 8 parcels were flagged.
- 6 flagged parcels were assigned to hub-manager escalation.
- 2 flagged parcels were assigned to proactive customer calls.
- 40 parcels received no action.

The classifier's test precision was 68.89% and recall was 75.61%. Some flagged parcels will not be delayed, and some genuinely delayed parcels will be missed. Predictions should support operational judgement rather than replace it. Prioritise long-distance and high-risk parcels early enough for teams to intervene.

## 6. Production Plan

1. **Accuracy:** Track regression MAE and RMSE, plus classification precision, recall, and F1-score on newly labelled shipments. Investigate if MAE exceeds 5 hours or classification recall falls below 70%.
2. **Reliability:** Keep the saved-model reload check and verify that reloaded predictions match the original predictions. The current reload check reports a maximum probability difference of 0.0.
3. **Reproducibility:** Preserve the ordered scripts, pinned requirements, fixed data splits, and model configuration. Rerun the pipeline from data generation through prediction to reproduce results.
4. **Consistency:** Use the shared cleaning and feature-building functions and the saved feature order during training and inference. Reuse the saved imputation medians for new shipments.
5. **Performance:** Measure prediction latency and check whether shipment batches are scored within the operational service-level target.
6. **Maintainability:** Keep cleaning, modelling, segmentation, packaging, and prediction in separate scripts. Store generated CSV results in `outputs/` and reusable model artefacts in `models/`.
7. **Monitorability:** Track weekly delayed share, missing required inputs after preprocessing, and the share of parcels flagged for action. Investigate if the weekly delayed share exceeds 30%, required fields remain missing after preprocessing, or the flagged share changes materially from its established baseline.
8. **Recall monitoring:** Once delivery outcomes become known, compare predictions with actual outcomes. Investigate if measured recall falls below 70%.
9. **Retraining schedule:** Review performance monthly and retrain when performance degrades or shipment patterns change materially. Validate a replacement model before deployment.
10. **Sale-event monitoring:** Compare shipments in the 15–28 September sale-event window, identified by `sale_event_flag`, with comparable sale-event periods where available. Do not judge sale-event performance solely against ordinary weeks because shipment volume and delivery conditions may differ.
11. **Data drift:** Monitor changes in distance, parcel weight, declared value, service type, hub tier, and sale-event frequency. Investigate material changes in feature distributions and model performance before relying on predictions.
12. **Human oversight:** Use predictions to prioritise investigation. Hub managers retain responsibility for escalation and customer communication.

The numeric triggers in this plan are proposed operational monitoring rules, not guarantees of future model performance.

## 7. Limitations

- **Synthetic data:** The pipeline uses generated data rather than real operational shipment records. Its metrics may not represent real-world performance, so validation on historical operational data is required before deployment.
- **Small test set:** The classification test set contains only 41 delayed parcels. Precision and recall may vary on future data.
- **Threshold selection:** The alert threshold was chosen using one validation split. Its performance may change with a different sample or delay cost.
- **Correlation versus causation:** Associations between distance, promised delivery time, hub tier, and delays do not establish that any one factor causes delays.
- **Distribution shift:** Sale events, seasonal demand, changes in hub operations, and changes in shipment mix may reduce model performance over time.
- **Model generalisation:** The reported metrics come from the current train/validation/test split. Performance on future shipments and different operational conditions may differ.
- **Operational integration:** The project produces CSV outputs and packaged model files; it has not yet been validated as a live production service.
